3.1 Architecture Overview

The system is a three-party client–server design: the faculty browser displays the QR code, the student phone scans and signs, and the server issues tokens, verifies scans and keeps the tamper-evident log. All communication uses HTTPS. The only channel that does not go through the network is the camera reading the projector.

3.2 Components

ComponentResponsibilitySecurity mechanism
Auth & RBACLogin, sessions, role checks (student / faculty / admin), ownership checksArgon2id, 256-bit session tokens stored as SHA-256, lockout after 5 failures
QR token serviceMints the QR content for the current 10-second windowHKDF-derived per-session key, HMAC-SHA256 tag (128-bit)
Device registrationBinds one ECDSA public key to each student accountRe-binding blocked; only admin can reset
Scan verifierRuns the nine ordered checks on every scanHMAC, time window, ECDSA verify, timestamp skew, nonce table
Attendance chainAppends records; verifies the whole chain on demandSHA-256 hash chain, chain head anchored in signed reports
Report signerBuilds and signs the session report on closeEd25519 over canonical JSON; private key encrypted at rest
Event logRecords rejections, logins, overrides, device resetsVisible to faculty (per session) and admin (global)

3.3 Key Hierarchy

MASTER_KEY  (32 random bytes, .env only, file mode 600, git-ignored)
 ├── HKDF(info = "qr-token|<session_id>")  →  per-session HMAC key for QR tokens
 └── HKDF(info = "report-key-wrap")         →  encrypts the Ed25519 private key on disk

Ed25519 signing key   keys/report_signing_key.pem   (encrypted PKCS#8)
Ed25519 public key    keys/report_signing_pub.pem   (published for verification)
Device keys           generated on each phone; server stores only public keys

Only one secret has to be protected on the server. A leaked per-session key lets an attacker forge QR codes for that one class, and does not reveal the master key or any other key.
