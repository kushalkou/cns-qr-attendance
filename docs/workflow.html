5.1 Attendance Flow: Faculty → Student → Server

StepStageWhat happens
1LoginUsers log in; passwords checked against Argon2id hashes; session cookie issued.
2Device registrationOnce per student: phone generates an ECDSA P-256 key pair; public key sent to the server and bound to the account.
3Start sessionFaculty starts a class; server creates a random session ID and derives its HMAC key with HKDF.
4Rotating QREvery 10 s the QR shows session_id.window.tag, where the tag is an HMAC of the session and window.
5Scan & signPhone reads the QR and signs token | user_id | timestamp | nonce with its private key.
6VerifyServer runs nine checks in order and rejects at the first failure (logged with the reason).
7RecordAccepted scan is appended to the SHA-256 hash chain.
8Close & signFaculty closes the session; server builds the present / absent report, pins the chain head and signs it with Ed25519.

5.2 QR Token Format

session_idwindowtag
8 hex chars, random per class⌊unix_time / 10⌋HMAC-SHA256(K_session, session_id ‖ window), first 16 bytes, base64url

Example: 8308bb93.179562491.i7obqhSNLAU_5sCEG_cVog. The server accepts the current window and the one before it, so a token is valid for at most 20 seconds.

5.3 Signed Scan Request

tokentsnoncesig
QR content as readphone time (s)144 random bits, base64urlECDSA P-256 / SHA-256 over token | user_id | ts | nonce

The user ID comes from the login session, not from the request body, so a student cannot claim to be someone else. The phone's private key never leaves the browser; WebCrypto creates it with extractable: false.

5.5 Chain Record and Signed Report

idsession_idstudent_idtsmethodactor_idnoteprev_hashhash
sequenceclasswhowhenqr / manualwho caused itoverride reasonh_(i-1)SHA-256(h_(i-1) ‖ JSON)

Report: course, faculty, start / close times, present list (with record IDs and hashes), absent list, counts, chain_head and chain_head_id, all signed with Ed25519 over canonical JSON (sorted keys, no spaces).
