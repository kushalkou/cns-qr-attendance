4.1 Functional Requirements

IDRoleRequirement
FR1AllLog in with username / USN and password; log out.
FR2StudentSign up, register one phone, scan the class QR, view own attendance percentage per course.
FR3FacultyStart a session, display the rotating QR, see present and rejected scans live.
FR4FacultyMark a student present manually with a mandatory reason (logged).
FR5FacultyClose a session and download the signed report; view defaulters (< 75%).
FR6AdminVerify the attendance chain, reset device bindings, unlock accounts, add faculty, view the security log.
FR7AnyoneVerify a downloaded report against the public key.

4.2 Non-Functional Requirements

  • Security: confidentiality of credentials, integrity of records, authenticity of scans, non-repudiation of reports.
  • Usability: a scan should take only a few seconds; works in a phone browser with no app install.
  • Performance: QR refresh every second on the faculty screen; scan verification in milliseconds.
  • Portability: runs on a laptop with one command (./run.sh); phones connect over Wi-Fi or a hotspot.
  • Auditability: every security-relevant event is recorded with time, user and IP.

4.3 Threat Model

Assets

Attendance records, session reports, user credentials, the master key and the report signing key.

Adversaries

AdversaryCapabilitiesGoal
Absent studentReceives photos / messages from friends in class, knows own passwordGet marked present remotely
Helping friendIn class, has own phone, may know the absent student's passwordMark the absent student present
Network attackerCan capture and resend requests on the same networkReplay or modify scans
Curious studentKnows the QR format, can call APIs directlyForge tokens, access faculty / admin functions
Insider with DB accessCan read and edit the SQLite fileChange records without being detected
Password guesserOnline login attemptsTake over an account

4.4 Assumptions

  • The server and its .env master key are not compromised.
  • Students do not hand their own unlocked phone to someone else (no QR scheme can detect this).
  • Each student registers their phone before a friend can (see the security analysis for this limitation and its fix).
  • Phone and server clocks agree within 60 seconds.
